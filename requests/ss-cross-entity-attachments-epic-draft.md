# Epic Draft da Solution Study ss-cross-entity-attachments

## Problem Statement
Oggi non esiste alcuna infrastruttura di allegati/file nell'applicazione (verificato: nessun uso di Firebase Storage nel codice, nessun `storage.rules`, nessuna sezione `storage` in `firebase.json`), e non esiste un modo per associare file generici (con descrizione) a un'entita' applicativa. Il problema non e' 'dove mettere i file su Google Drive' — quella e' una soluzione proposta dall'operatore per uno dei sotto-problemi, non ancora decisa — ma: (1) fornire una capability di allegati riusabile trasversalmente da piu' domini (oggi `device-requests`, in futuro le iniziative/progetti speciali) invece di reinventare storage/modello-dati/RBAC per ognuno, e (2) farlo rispettando un perimetro di visibilita' e di autorizzazione gia' deciso (solo staff — admin e volontari, mai il richiedente/famiglia — con differenziazione admin/volontario su modifica ed eliminazione). La sequenza di sviluppo confermata dall'operatore vuole questa capability costruita e funzionante *prima* di agganciarla a qualunque dominio consumer: questo studio riguarda esclusivamente la capability di base (storage, modello dati, RBAC, superficie funzionale), non l'integrazione con `device-requests` ne' con i futuri progetti speciali, che restano un passo successivo separato.

## Opzione scelta
- Id: opt-a-firebase-storage-native
- Nome: Cloud Storage nativo, RBAC interamente in Cloud Function con signed URL (nessun proxy di byte, nessuna Storage Rule per il perimetro RBAC)
- Summary: I file fisici vivono in un bucket Cloud Storage dedicato esclusivamente agli allegati (path del tipo `attachments/{entityType}/{entityId}/{attachmentId}/{filename}`), provisionato da zero per questo progetto. Le Cloud Function callable (`uploadAttachment`/`downloadAttachment`/`listAttachments`/`updateAttachmentDescription`/`deleteAttachment`) fanno da unico punto di enforcement RBAC (stesso pattern gia' in uso ovunque nel backend: lettura `users/{uid}.role` + ownership dal documento allegato), in codice TypeScript testabile — non in regole dichiarative. Per upload e download, la function non fa da proxy dei byte: dopo aver verificato l'RBAC, genera una signed URL V4 a breve scadenza (azione `write` o `read`) e la restituisce al client, che trasferisce i byte direttamente client↔GCS. Le Storage Security Rules restano quindi marginali (bucket privato, nessun accesso diretto via SDK client Firebase): il perimetro di sicurezza reale e' interamente la generazione della signed URL post-RBAC, dato che le signed URL sono chiamate dirette all'API GCS e bypassano le Firebase Storage Rules per costruzione. I metadati (descrizione, `uploadedBy`, `entityType`/`entityId`, `storagePath`) vivono in una collection Firestore di primo livello `attachments/{attachmentId}`, coerente col precedente `checklistItems`. L'eccezione superadmin si risolve con un ruolo IAM nativo GCS (es. `roles/storage.admin` o `storage.objectAdmin`) assegnato a livello del solo bucket dedicato agli account superadmin, senza introdurre alcun sistema esterno.

## Vincoli
- Nessuna infrastruttura di storage esiste oggi nel progetto (verificato: nessun `getStorage`/`uploadBytes` nel codice, nessun `storage.rules`, nessuna sezione `storage` in `firebase.json`, bucket Storage non provisionato): qualunque opzione la introduce da zero, incluse le regole di sicurezza.
- RBAC gia' deciso dall'operatore (2026-09-06), non negoziabile in questo studio: visibilita' solo staff (admin + volontario, mai richiedente/famiglia); upload consentito sia ad admin sia a volontario; modifica/eliminazione — admin su qualunque allegato, volontario solo su quelli caricati da se stesso.
- Perimetro entita' gia' deciso: solo entita' di alto livello (`deviceRequest`, futuri progetti speciali/iniziative), non a livello di singolo item di checklist.
- Contenuto gia' deciso: file generico con descrizione libera, non tipizzato per categoria di documento.
- Scope di questo studio limitato alla capability di base (sequenza confermata dall'operatore): non tratta l'integrazione con `device-requests` (step 2) ne' con `ir-special-projects-initiatives` (step 2, dominio non ancora implementato) — qualunque opzione deve restare integrabile in modo leggero da un futuro consumer, senza gia' impegnarsi sulla UI/RBAC specifica di quei domini.
- Precedente di modellazione dati gia' stabilito nello stesso repo: la collection `checklistItems` (decisione dello studio `ss-checklist-item-model`, gia' 'decided') e' una collection Firestore di primo livello con riferimento all'entita' proprietaria, non una subcollection — coerente con l'osservazione della richiesta che questo e' il pattern 'che meglio si presta a essere capability di base riusabile'. Le opzioni sotto adottano questo stesso pattern per i metadati degli allegati (`attachments/{attachmentId}` con `entityType`/`entityId`), per coerenza con la scelta di modellazione piu' recente e analoga in questo repo, non per assunzione arbitraria.
- Precedente RBAC 'ownership' gia' esistente nel dominio `shipments` (`deleteShipmentRequest`): 'l'admin puo' eliminare qualsiasi richiesta; il volontario solo le proprie in stato pending' — stesso pattern admin-vs-owner richiesto qui per modifica/eliminazione allegati, gia' precedente nel repo e non un caso nuovo da inventare.
- Convenzione di progetto `security_logging`: ogni Cloud Function deve loggare inizio, fine ed errori in `securityLogs` via `logSecurityEvent` — si applica anche a qualunque nuova funzione di questa capability, indipendentemente dal backend scelto.
- Nessuna dipendenza a oggi verso API Google esterne lato server: `functions/backend/package.json` dichiara solo `firebase-admin`, `firebase-functions`, `jsonwebtoken`. Il progetto usa gia' Google come identity provider (Google OAuth per il login di volontari/admin, dominio `auth`), ma quel client OAuth end-user e' un credential type distinto da quanto servirebbe per un'integrazione Drive API server-to-server (service account con domain-wide delegation, o OAuth server-side dedicato): l'assenza di precedenti riguarda specificamente l'uso server-side di API Google non-Firebase, non l'uso di Google in generale nel progetto.
- Il backend di storage (Google Drive dedicato vs Firebase/Cloud Storage nativo) e' esplicitamente non deciso: l'operatore lo ha proposto in conversazione (2026-09-06) ma la richiesta stessa impone di pesarlo con trade-off espliciti, non di assumerlo.
- Eccezione RBAC confermata dall'operatore (2026-09-06), aggiuntiva rispetto all'RBAC di cui sopra: un numero ristretto di 'superadmin' (ruolo oggi inesistente in app: solo admin/volontario/organizer, verificato) ha accesso diretto nativo allo spazio di storage, fuori dal proxy applicativo, per supervisione/backup. Per quei soli account l'RBAC per-utente/ownership deciso sopra non si applica — accettato esplicitamente dall'operatore come costo del canale. Il meccanismo di concessione/mantenimento dell'elenco superadmin (nuovo valore di `users/{uid}.role` vs lista fuori Firestore) non e' ancora deciso, indipendentemente dal backend scelto.
- Ripensamento confermato dall'operatore (2026-09-06, dopo il primo refine): i costi di storage/trasferimento su Cloud Storage nativo sono minimi — l'argomento 'spazio a costo prevedibile/gestito a mano' che nel giro di refine precedente aveva pesato a favore di Drive e' esplicitamente ritirato dall'operatore, non solo derubricato a criterio organizzativo non pesabile tecnicamente: non va piu' trattato come un pro reale di nessuna opzione in questo studio.
- Verificato in questo giro di refine (ricerca su documentazione Google Cloud ufficiale, 2026-09-06), in risposta alla richiesta esplicita dell'operatore di controllare l'affermazione del refine precedente: 'Option A richiederebbe IAM a livello di intero progetto GCP, non della sola cartella allegati' NON e' accurato. Cloud Storage supporta l'assegnazione di ruoli IAM (inclusi `roles/storage.admin` e `roles/storage.objectAdmin`) direttamente a livello di singolo bucket, non solo di progetto: il bucket e' esso stesso una risorsa IAM, e un binding a quel livello si applica solo al bucket indicato (e agli oggetti al suo interno), non al resto del progetto. Poiche' oggi non esiste alcuna infrastruttura Storage nel progetto (vedi vincolo sopra), un bucket dedicato esclusivamente agli allegati rende un binding IAM a livello di bucket gia' scoped esattamente alla capability allegati, senza bisogno di funzionalita' aggiuntive. Per uno scoping ancora piu' fine (prefisso/cartella all'interno di un bucket condiviso in futuro con altri usi Storage non-allegati), Cloud Storage supporta anche IAM Conditions basate su `resource.name.startsWith(...)`, documentate da Google per ruoli standard come `storage.objectViewer`/`storage.objectAdmin` — ma la documentazione Google stessa contiene una nota di ambiguita' non risolta da questa ricerca ('gli attributi API per Cloud Storage sono supportati solo nei Credential Access Boundaries', in apparente tensione con gli esempi di condizioni su prefisso documentati altrove). Questa ambiguita' non e' pero' rilevante per la decisione di questo studio: un bucket dedicato (scoping a livello di intero bucket, non di prefisso) e' gia' sufficiente per il caso d'uso superadmin confermato, e non richiede IAM Conditions.

## Concern rilevanti
- [high] Con le signed URL che bypassano le Storage Rules, la Cloud Function e' l'unico punto di enforcement RBAC per l'intera capability: un errore di logica nel controllo di ruolo/ownership prima della generazione della signed URL non ha alcuna rete di sicurezza aggiuntiva a valle. - Mitigazione: Suite di test unitari/di integrazione dedicata per ogni combinazione ruolo/ownership (admin, volontario proprietario, volontario non proprietario) sulla funzione che genera la signed URL, trattata con lo stesso rigore gia' richiesto per la superficie RBAC piu' sensibile del backend, prima del deploy.
- [medium] Il completamento di un upload e' osservabile via trigger `onObjectFinalized`, ma il completamento di un download non ha alcun equivalente nativo GCS: la convenzione `security_logging` puo' quindi registrare solo l'emissione della signed URL di download, non l'avvenuto download. - Mitigazione: Decidere esplicitamente, prima dell'implementazione, se 'signed URL di download emessa' e' un proxy accettabile per la convenzione `security_logging` su questa capability, oppure se serve un flusso alternativo (es. redirect controllato dalla function) per un logging di completamento piu' fedele — accettando in quel caso di reintrodurre parte del proxy di byte che questa opzione vuole evitare.
- [medium] La generazione di signed URL V4 dal service account di runtime di default di una Cloud Function richiede che quel service account abbia il ruolo `roles/iam.serviceAccountTokenCreator` su se stesso (concessione IAM una tantum): se omessa, la chiamata fallisce a runtime con un errore di permesso, non in fase di build/deploy. - Mitigazione: Documentare questa concessione IAM esplicitamente nel checklist di deploy della capability e verificarla empiricamente prima di impegnarsi sull'effort stimato (vedi spike sotto).

## Opzioni scartate
- Google Drive dedicato, sempre mediato da Cloud Function proxy (nessun link diretto al client) (opt-b-drive-proxy-function): Prima dipendenza esterna del backend verso un'API Google non-Firebase: nuova libreria (es. `googleapis`/`google-auth-library`), nuove credenziali da gestire come secret, nuovo punto di fallimento (quota/latenza Drive API) distinto da Firestore.
- Google Drive dedicato, RBAC delegato ai permessi di condivisione Drive (link diretti al client) (opt-c-drive-native-sharing): Non replica il perimetro RBAC granulare gia' deciso (volontario puo' modificare/eliminare solo i propri allegati): sincronizzare permessi di condivisione Drive per singolo utente con lo stato Firestore (ruolo, assegnazione, disattivazione) e' una capability aggiuntiva non richiesta dalle altre opzioni, con finestre di inconsistenza reali (es. volontario disattivato che mantiene l'accesso Drive finche' la sincronizzazione non lo revoca).
